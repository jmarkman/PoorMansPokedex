## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Add a MockingTools folder to PoorMansPokedex.Test with reusable test-data builders and HTTP mocking helpers used by the rest of the test suite.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 MockingTools contains one or more builder classes/methods that construct different variations of PokedexEntry (e.g. a fully-populated entry, a minimal entry, an entry with null/empty collections) for use across test fixtures
- [x] #2 MockingTools contains a helper that constructs a mocked HttpMessageHandler (using Moq Protected setup on SendAsync) and returns an HttpClient built from it, so tests can control the HttpResponseMessage (status code and JSON body) returned for a given request, following the approach at https://gingter.org/2018/07/26/how-to-mock-httpclient-in-your-net-c-unit-tests/
- [x] #3 The HttpMessageHandler helper supports configuring different response status codes and JSON bodies per test case
- [x] #4 Solution builds successfully
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Add a MockingTools folder under PoorMansPokedex.Test with a reusable PokedexEntry builder in its own file; provide fresh minimal and fully populated entries plus empty-collection/nullable-nested-data variations consistent with the Core model nullability. 2. Add a separate mocked HTTP helper that uses Moq Protected setup for HttpMessageHandler.SendAsync, accepts per-test response status and JSON body (and can match the request), and returns an HttpClient built on the configured handler while keeping the handler mock accessible for request assertions. 3. Use System.Net response/content types and UTF-8 JSON consistently, avoid live network dependencies, and limit changes to reusable test utilities without adding endpoint/wrapper test cases in this task. 4. Build the solution and verify the helper API compiles for downstream test use.
<!-- SECTION:PLAN:END -->
