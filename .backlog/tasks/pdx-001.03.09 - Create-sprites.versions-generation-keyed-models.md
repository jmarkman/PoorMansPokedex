## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Model the "sprites.versions" sub-object from the magnemite payload. This tree is dynamically keyed by generation label (generation-i through generation-ix at time of writing) and, within each generation, by version-pair label (e.g. red-blue, gold, platinum, x-y, icons). Per prior decision, model this with a fixed class per known generation rather than a dictionary, naming each generation class by converting its Roman numeral to an integer (e.g. "generation-i" -> class Generation1, "generation-iv" -> class Generation4), each as its own file in PoorMansPokedex.Core/Models, with a property per version-pair key mapped via JsonPropertyName to that exact JSON key (e.g. a Generation1 class with RedBlue, Yellow, RedGreenJapan properties). Each version-pair value itself has a different, irregular set of nullable string sprite fields (and sometimes a nested "animated" or "icons" sub-object) depending on generation and pair; reuse a shared sprite-variant class across pairs wherever two pairs genuinely share the same field set, but do not force-fit mismatched shapes into one shared class. Fetch the live payload at https://pokeapi.co/api/v2/pokemon/magnemite to confirm the exact generations, pair keys, and fields in sprites.versions before implementing, since this is not restated verbatim here. If a pair exposes a field shape not already covered by the naming rules already agreed upon for this feature (e.g. the nested "animated" or "icons" objects), pause and confirm the class/property naming with the user before implementing rather than deciding unilaterally. Wire the finished Versions property (mapped to "versions") into the Sprites class created in the previous subtask.
<!-- SECTION:DESCRIPTION:END -->
