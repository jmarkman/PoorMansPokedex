## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Umbrella task for Feature 1, Item 3: build the System.Text.Json deserialization target for GET https://pokeapi.co/api/v2/pokemon/{name|id} (sample payload: https://pokeapi.co/api/v2/pokemon/magnemite) inside PoorMansPokedex.Core/Models. Every nested, non-primitive JSON object gets its own class file, PascalCase C# property names are mapped back to the original JSON names with [JsonPropertyName], and this is tracked entirely via this tasks subtasks. The payload is large and irregular (repeated name/url pairs, a type object that collides with System.Type, generation-labeled data, and a deeply/dynamically-keyed sprites.versions history tree), so the user has already made the following naming/structure decisions for all child subtasks to follow: (1) every repeated {name,url} JSON object gets its own per-context class (Ability, Species, Item, Move, Stat, Version, VersionGroup, MoveLearnMethod, Generation, Form) rather than one shared generic class; (2) the nested object under the "type" JSON key is modeled as a class named ElementalType; (3) the sprites.versions tree is modeled with fixed classes per known generation, naming them with the Roman numeral converted to an integer (e.g. "generation-iv" -> class Generation4, following the Generation4 naming pattern for any other generation-numeral-derived name). If, while working a child subtask, a further class/property naming decision is encountered that was not already settled by these rules or by the subtasks own description, pause and ask the user rather than deciding unilaterally.
