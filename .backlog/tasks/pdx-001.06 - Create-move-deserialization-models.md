## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
In PoorMansPokedex.Core/Models, add the wrapper classes for the moves array of the pokemon payload (https://pokeapi.co/api/v2/pokemon/magnemite), which is the largest and most deeply nested array in the response (each move can carry many version-group learn-method entries), building on the shared Move, VersionGroup, and MoveLearnMethod classes from the shared-resources task.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 A PokemonMove class represents moves array entries (a Move property, and a VersionGroupDetails list)
- [x] #2 A PokemonMoveVersionGroupDetail class represents moves[].version_group_details entries (LevelLearnedAt int from level_learned_at, a VersionGroup property, a MoveLearnMethod property, and a nullable Order int)
- [x] #3 Each class lives in its own file in Models per architecture.instructions.md
- [x] #4 Solution builds successfully
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Add PoorMansPokedex.Core/Models/PokemonMove.cs for entries in the root moves array, mapping the nested move reference to the existing Move model and version_group_details to a List<PokemonMoveVersionGroupDetail> initialized empty.
2. Add PoorMansPokedex.Core/Models/PokemonMoveVersionGroupDetail.cs, mapping level_learned_at to int, version_group and move_learn_method to the existing shared resource types, and order to nullable int.
3. Follow existing file-scoped namespace, separate-file architecture, explicit JsonPropertyName mappings, and nullable-enabled Core conventions; do not modify the shared reference models or unrelated files.
4. Verify the property names/types and JSON mappings against the task criteria with a representative moves payload, then build PoorMansPokedex.slnx.
<!-- SECTION:PLAN:END -->
